# Byte-for-byte output-equivalence oracle for COBOL batch: empirical feasibility

Scope: can an oracle that runs the original COBOL and the translated Java on pinned inputs and compares datasets byte for byte be built from open tooling? Everything below marked **[empirical]** was run in this Linux container (Ubuntu 24.04, x86_64, 2 vCPU) on 2026-10-03/04; the artifacts are under `/home/claude/cobol-research/tools/` (`nist/` = NIST run, `runs/omp/` = course programs, `runs/carddemo/` = CardDemo batch). Web sources are cited inline; local evidence is cited by file path.

## Key question 1: Can GnuCOBOL be installed or built here?

### Takeaway
Yes, in about one minute, from Ubuntu's own repository: `apt-get update` then `apt-get install -y gnucobol3` gives GnuCOBOL 3.1.2 with the BDB indexed-file handler, GMP arithmetic, and all dialect configs (`ibm.conf`, `mvs.conf`, `cobol85.conf`). No source build was needed; the GitHub mirror of the 3.x source (OCamlPro/gnucobol, 2026-09-17 head) was still essential because it carries the NIST harness scripts.

### Cited Findings
- `apt-get install -y gnucobol` failed before `apt-get update` ("Unable to locate package gnucobol"); after `apt-get update` (one third-party repo 403'd through the proxy, harmless) Ubuntu noble offers `gnucobol` (metapackage), `gnucobol3` 3.1.2-5.1ubuntu1 and `gnucobol4` 4.0-early-20200606. **[empirical]** — shell transcript, this session.
- `apt-get install -y gnucobol3` exited 0, installing `libcob4-dev`, `libgmp-dev`, `gnucobol3`. `cobc --version` reports `cobc (GnuCOBOL) 3.1.2.0`, built Apr 14 2024 with gcc 13.2. **[empirical]**
- `cobc --info`: 64-bit, little-endian, `native EBCDIC: no`, sequential handler built-in, indexed handler **BDB**, math **GMP**, XML libxml2, JSON not found, screen ncursesw. Dialect configs in `/etc/gnucobol/`: acu, bs2000, cobol2002, cobol2014, cobol85, default, ibm, mf, mvs, realia, rm, xopen (each with a `-strict` variant). **[empirical]**
- Build dependencies for a source build are also all available from apt (autoconf, automake, libtool, gettext, help2man, texinfo, bison, flex, libdb-dev, libncurses-dev, libxml2-dev, libjson-c-dev installed in ~2 min) — so a from-source build of the 3.x mirror is feasible here if a newer compiler is wanted (not attempted; apt was sufficient). **[empirical]**
- The GitHub mirror at `/home/claude/cobol-research/corpus/gnucobol` is `https://github.com/OCamlPro/gnucobol`, branch `gitside-gnucobol-3.x`, last commit deb0034 2026-09-17; it contains `tests/cobol85/` (the NIST harness: `EXEC85.conf.in`, `expand.pl`, `report.pl`, `summary.pl`, expected `*.txt` per module). **[empirical]**

### Inferences
- The Ubuntu package is the fastest route to a reproducible oracle environment: a Dockerfile with `apt-get install gnucobol3` and a pinned image digest fixes the compiler version, which is itself a determinism requirement (see Q2).
- GnuCOBOL 3.2 (2023) exists upstream; the harness in the 3.x mirror already assumes it (one flag, `-Wno-goto-section`, is unknown to 3.1.2). Either pin the harness to the compiler's own release tarball or patch as done here.

### Gaps
- The GnuCOBOL 3.2/4.x source build was not timed here (not needed). Known from the FAQ to take a few minutes on a modern machine; unverified in this container.

## Key question 2: Compile and run real programs; determinism; what must be pinned

### Takeaway
Fourteen real programs were compiled and nine run end to end: five from the Open Mainframe Project course, four CardDemo batch programs (including the transaction-posting job against five indexed files and a report job with an emulated SORT step), plus 426 NIST programs. Outputs were byte-identical across repeated runs **once** the clock was fully pinned (`COB_CURRENT_DATE` with hundredths and zone), DD names were bound by `DD_<name>` environment variables, and comparisons were made on the logical record stream rather than on the BDB index file. Several small IBM-isms had to be patched or stubbed; each one is a thing the oracle harness must own.

### Cited Findings

**Open Mainframe Project course programs** (`corpus/cobol-programming-course/.../Labs/cbl/*.cobol`) **[empirical]**:
- `HELLO`, `PAYROL00` compile unchanged with `-std=ibm`. `CBL0001/2/5/6/33` fail with `syntax error, unexpected ENVIRONMENT` because `PROGRAM-ID. CBL0001` has no terminating period (IBM Enterprise COBOL accepts it; GnuCOBOL 3.1.2 does not, even with `-frelax-syntax-checks`). A one-line sed adding the period fixes all five. `CBL0002` is the course's deliberate bug (`PRINT-REX` undefined).
- The course's data file `Labs/data/data` is **EBCDIC** (7650 bytes = 45 × 170-byte records: `X(8)`, two `S9(7)V99 COMP-3`, then text). Run unconverted, the program produced correct money columns (COMP-3 is codepage-independent) and garbage text columns. A field-aware transcoder (cp037→ASCII for `PIC X`, bytes passed through for `COMP-3`) was written in 15 lines of Python; the report then read correctly (`17891797   $10,000.00      $188.74WASHINGTON ...`). Byte-blind `iconv` would corrupt the packed fields.
- `CBL0001` run three times on the same input: identical SHA-256 (`a655cdaa…`) each time.
- `CBL0005` prints `FUNCTION CURRENT-DATE`; with `COB_CURRENT_DATE="2020-01-02 03:04:05"` two runs produced identical output (`a0134b24…`) and the report header read `Year 2020 Month 01 Day 02`.
- `CBL0033` does `CALL 'HELLO'`: fails at run time with `libcob: error: module 'HELLO' not found`, rc=1; fixed by compiling HELLO as a module (`cobc -m`) and setting `COB_LIBRARY_PATH`. This is the STEPLIB equivalent.

**CardDemo batch** (`corpus/aws-mainframe-modernization-carddemo/app`) **[empirical]**:
- Of ten batch programs compiled with `cobc -x -std=ibm -I app/cpy`: `CBACT01C, CBACT02C, CBACT03C, CBCUS01C, CBTRN01C, CBTRN02C, CBTRN03C` compiled clean. `CBACT04C` and `CBSTM03B` fail with `executable program requested but PROCEDURE/ENTRY has USING clause` (they take a JCL `PARM`; need `-m` or a driver). `CBSTM03A` fails inside copybook `CUSTREC.cpy` (`invalid PICTURE character '2'`, unbalanced parentheses) — a copybook written for a different compiler option set.
- The repo ships flat data in both EBCDIC (`data/EBCDIC/*.PS`, no line terminators, e.g. ACCTDATA 15000 bytes = 50 × 300) and ASCII (`data/ASCII/*.txt`, with `\n`, some with `\r\n`; 15050 bytes). The ASCII `cardxref.txt` has a 36-byte short line amid 50-byte records. The harness must strip terminators and pad to the JCL `LRECL` before use.
- The programs read VSAM KSDS files; JCL (`ACCTFILE.jcl` etc.) defines them with IDCAMS `DEFINE CLUSTER ... KEYS(11 0) RECORDSIZE(300 300)` and loads them with `REPRO`. A 30-line COBOL loader (`load_*.cbl`, indexed file, sequential WRITE) stands in for REPRO; keys are taken from the IDCAMS statements. Loading `DISCGRP` as shipped gave file status `21` (key out of sequence) on 49 of 51 records: the ASCII flat file is not in key order (REPRO into an empty KSDS would reject this too). Pre-sorting fixed it.
- `CBACT01C` (READACCT job) aborted with `libcob: error: module 'COBDATFT' not found`, rc=1, empty outputs: it calls an **assembler** routine (`app/asm/COBDATFT.asm`) for date formatting. Outputs were still identical between runs (both empty). Assembler callees are outside any COBOL translator's reach and must be reimplemented or stubbed.
- All four programs end errors with `CALL 'CEE3ABD' USING ABCODE, TIMING` (Language Environment abend). A 10-line COBOL stub `CEE3ABD` (DISPLAY the code, `MOVE ABCODE TO RETURN-CODE`, `STOP RUN`) made abends observable: `U999` surfaced as process exit 231 (999 mod 256) — a harness must capture the abend code itself, not rely on the 8-bit exit status.
- **POSTTRAN job** (`CBTRN02C`): 300 daily transactions against TRANFILE (empty KSDS), XREFFILE, ACCTFILE, TCATBALF; writes rejects to DALYREJS. Ran to completion: `TRANSACTIONS PROCESSED :000000300 / REJECTED :000000043`, rc=4, 257 records written to the transaction KSDS, 18490-byte reject file, and TCATBAL records created on the fly. Two runs with `COB_CURRENT_DATE="2024-03-01 12:00:00"`: DALYREJS, ACCTFILE and TCATBALF images **identical**, but TRANFILE differed in every record at column 326 (`0` vs `2`). Cause: that env setting pins only to the second; `FUNCTION CURRENT-DATE` still returned live hundredths (`...088`, `...089` on successive runs — confirmed with a 7-line probe). Setting `COB_CURRENT_DATE="2024-03-01 12:00:00.00 +00:00"` and `TZ=UTC` made the **logical** unload of TRANFILE identical (`aed61744…`) across runs.
- Even then the raw BDB `.ksds` files differed in 7 bytes (char 53 onward: BDB page metadata). Byte comparison of indexed files must therefore be on an unload in key order (the 35-line `unload.cbl` here), never on the physical index file. Sequential outputs can be compared raw.
- **TRANREPT job**: its JCL (`jcl/TRANREPT.jcl`) is `IDCAMS REPRO` → `SORT FIELDS=(TRAN-CARD-NUM,A) INCLUDE COND=(TRAN-PROC-DT,GE,start,AND,LE,end)` → `CBTRN03C`. The SORT step was emulated with a 50-line COBOL `SORT ... WITH DUPLICATES IN ORDER INPUT PROCEDURE` taking the dates from env vars; `CBTRN03C` then read the sorted file plus three KSDS lookups and a DATEPARM card. Two complete runs: sorted intermediate, 60914-byte report and stdout all identical (`a7d14a96…`, `19b7f04f…`). The report's `Grand Total ... 123,816.50` reconciles with the 257 posted transactions.
- Two harness mistakes during this were instructive: a 30-byte DATEPARM record against an `FD ... PIC X(80)` gave file status `04` (record length mismatch → program abended U999); and the parm's layout (`YYYY-MM-DD␠YYYY-MM-DD`, a 1-byte filler between the dates) is only visible in WORKING-STORAGE, not JCL, and the actual dataset `AWS.M2.CARDDEMO.DATEPARM` is not in the repo. Datasets created on the mainframe outside the repo are a recurring hole in open corpora.
- **SORT stability**: 20,000 records with 10 distinct keys, `SORT ... USING/GIVING` without `WITH DUPLICATES IN ORDER`: three runs identical, order within equal keys preserved (stable), and identical again with `COB_SORT_MEMORY=2M` forcing the disk-spill path. GnuCOBOL's sort is deterministic and effectively stable; DFSORT's is not guaranteed stable without `EQUALS`, so a translator or oracle must not assume stability was intended by the original program.

**NIST suite** (see Q4): 426 programs compiled and run in 96 s wall clock. **[empirical]**

### Inferences
- Pinning list for the original lane, from what actually broke here: (1) compiler version and dialect flags (`-std=ibm`, `-fsign`, dialect `.conf`); (2) every `ASSIGN` name → path via `DD_<name>` (resolution order in `libcob/fileio.c` `cob_chk_file_mapping`: `DD_x`, then `dd_x`, then `x`, then `COB_FILE_PATH` prefix); (3) `COB_CURRENT_DATE` **with** fractional seconds and zone, plus `TZ`; (4) `COB_LIBRARY_PATH` for every dynamically called module (STEPLIB); (5) stubs for LE/assembler callees (`CEE3ABD`, `COBDATFT`, and by extension `IGZ*`, `CEEGMT`, DB2/CICS preprocessor stubs); (6) `SYSIN` as stdin bytes and `PARM` via a driver; (7) record formats: LRECL/RECFM per DD, `COB_VARSEQ_FORMAT` for RECFM=V (default `0` = 2-byte big-endian length + 2 NULs, not IBM's RDW), `COB_LS_FIXED`/`COB_UNIX_LF` for line-sequential; (8) initial state of every indexed/relative file, loaded in key order; (9) `COB_SET_DEBUG`, `COB_SWITCH_n`.
- `RANDOM`: `FUNCTION RANDOM` was not exercised by any corpus program here; it is seedable in COBOL (`RANDOM(seed)`) but an unseeded call is not pinned by any env var found in `runtime.cfg`. The oracle should flag unseeded `RANDOM` as a non-equivalence source at translation time.
- The fact that `COB_CURRENT_DATE` without fractional seconds leaked hundredths into a persisted dataset is exactly the kind of subtlety the oracle exists to catch; the harness should always run the original lane twice and refuse to compare against Java until the original is self-identical.

### Gaps
- Nothing here exercised REPORT WRITER output to SYSOUT with carriage control, `WRITE ... AFTER ADVANCING` to a printer file in IBM RECFM=FBA, or `ACCEPT FROM SYSIN` in batch; those formats (ANSI control characters in column 1) need a documented normalization choice.
- `CBACT04C` (interest calculation, takes PARM) and the statement programs were not run; the former needs a PARM driver, the latter a copybook fix.

## Key question 3: Representing JCL-driven batch without a mainframe

### Takeaway
GnuCOBOL covers the program-level pieces (DD-name binding by `DD_` env vars, native `SORT`, indexed files via BDB, return codes), but nothing in it understands a job: steps, `COND`/`IF`, `DISP`, GDGs, concatenation, `SYSOUT`, utilities (IDCAMS, IEBGENER, SORT control cards). Open-source JCL interpreters are scarce and immature; commercial ones exist (Micro Focus/Rocket, J2U). A Hercules + MVS 3.8j (TK4-/TK5) lane gives real JES2, DFSORT-era SORT, VSAM and an **OS/VS COBOL** (1974-standard) compiler for free — valuable for a second opinion on IBM semantics, but it cannot compile COBOL-85/Enterprise COBOL code as written, and z/OS itself cannot legally be run on it.

### Cited Findings
- GnuCOBOL file mapping: `static const char *const prefix[] = { "DD_", "dd_", "" };` and `cob_chk_file_mapping()` checks those env names for an ASSIGN word with no directory separator, then prefixes `COB_FILE_PATH` if set; mapping is on by default (`filename-mapping: yes` in `config/default.conf`). — `/home/claude/cobol-research/corpus/gnucobol/libcob/fileio.c` lines 568, 1198–1275 **[empirical, source read]**
- `runtime.cfg` documents `COB_FILE_PATH` (default `.`), `COB_VARSEQ_FORMAT` (0..3; 0 = "2 byte record length (big-endian) + 2 NULs"), `COB_LS_FIXED`, `COB_LS_NULLS`, `COB_SYNC`, `COB_SORT_MEMORY` (default 128M, "if this size is exceeded the SORT will be done on disk"), `COB_SORT_CHUNK`, `COB_CURRENT_DATE` ("specify an alternate Date/Time ... a missing offset partial setting is allowed"). — `/etc/gnucobol/runtime.cfg` **[empirical]**
- GnuCOBOL has native `SORT`/`MERGE` statements (used above to stand in for a DFSORT step); it has no external SORT utility, no DFSORT control-card parser, and no IDCAMS. **[empirical: the SORT step had to be hand-written]**
- A GitHub topic search for JCL under the COBOL language filter returned ~20 repos, all course material or sample programs; "None of these repositories appear to be JCL interpreters or batch emulators." — [GitHub topics: jcl](https://github.com/topics/jcl?l=cobol)
- `roberjo/mainframe-frontier` is a Rust "JES-style job runner" over GnuCOBOL 3.2 in IBM dialect: supports JOB/EXEC (PGM, PARM, COND with EVEN/ONLY), DD with DSN/DISP/SYSOUT/DUMMY/DCB, catalog, GDGs `(+1)/(0)/(-1)`, `&&TEMP`, a DFSORT subset (INCLUDE/OMIT/SUM), IDCAMS, IEBGENER, IEFBR14; **not** PROCs, IF/THEN/ELSE, DD concatenation, VSAM or restart. Apache-2.0, 0 stars, 5 commits — very early. — [GitHub: roberjo/mainframe-frontier](https://github.com/roberjo/mainframe-frontier)
- On the GnuCOBOL users list the JCL-on-Unix options named were commercial or converters: J2U (commercial JCL interpreter), a UV Software JCL→ksh converter, Micro Focus's JCL interpreter, and a Perl VSE-JCL converter. — [gnucobol-users 2015-07](https://lists.gnu.org/archive/html/gnucobol-users/2015-07/msg00015.html)
- Hercules FAQ on legality: "OS/360 (PCP, MFT and MVT) is in the public domain, as far as we know"; MVS 3.8, VM/370 and DOS/VS were systems "for which IBM did not charge a license fee" and their status is "somewhat murky"; "z/OS, z/VM, z/VSE, OS/390, VM/ESA, or VSE/ESA" are "definitely licensed to a particular machine", with only four narrow legal paths (licensed P/390, licensed mainframe, DR provisions, IBM DemoPkg for employees/partners). — [SDL Hercules FAQ](https://sdl-hercules-390.github.io/html/hercfaq.html)
- Jay Moseley's install guide: MVS 3.8 "appeared to be in the status of Public Domain software and was available for order directly from IBM as a 'no charge' product"; a hand install is ~111 minutes of phases, "a few hours" for a first-timer; TK5 bundles "a huge set of utilities and bonus MVS programs". — [jaymoseley.com](https://www.jaymoseley.com/hercules/installMVS/iMVSintroV8.htm)
- cbttape.org calls MVS 3.8 "the last true free sourced-included version of MVS". — [cbttape.org](https://www.cbttape.org/mvs38.htm)
- Ready-made TK5 distributions exist as Docker images (e.g. `joergschultzelutter/tk5-hercules`, `praths/mvs-tk5`), i.e. practical cost is near zero. — [GitHub: tk5-hercules](https://github.com/joergschultzelutter/tk5-hercules); [Docker Hub: praths/mvs-tk5](https://hub.docker.com/r/praths/mvs-tk5)
- A 2025 write-up of exactly this use (COBOL vs Java equivalence on an emulated mainframe) ran SDL Hercules 4.9.1 + MVS 3.8j TK4- Update 08 with the **OS/VS COBOL compiler (IKFCBL00)**; obstacles: no `ORGANIZATION IS INDEXED` in the program (S0C4; had to write sequential then IDCAMS REPRO into VSAM), no inline `PERFORM ... END-PERFORM`, a `IKF0015I-C BUF PARM TOO SMALL` fix in the compile proc, VSAM `UNIQUE` to dodge suballocation exhaustion; Java needed `BigDecimal` with `HALF_UP` to match packed-decimal results. Hercules build ~20 min on m5.xlarge, IPL ~20 s, ~$0.19/h. They compared at the database layer, not byte for byte, and proved six positions across two funds. — [dev.to: Zero Variance](https://dev.to/banuap/zero-variance-proving-cobol-to-java-semantic-equivalence-with-a-live-mainframe-emulator-on-aws-1ani)

### Inferences
- The realistic design is a **job-model DSL** (or a strict JCL subset parser) owned by the oracle itself: parse JOB/EXEC/DD/COND/IF, resolve DSN→path and GDG generations, call GnuCOBOL binaries with `DD_*` env, interpret `IEFBR14`/`IEBGENER`/`IDCAMS REPRO|DELETE|DEFINE`/`SORT` with a DFSORT-subset implementation, propagate step return codes and apply `COND`. The CardDemo JCL above needed only PGM, DD DSN/DISP, IDCAMS DEFINE/REPRO/DELETE, SORT FIELDS/INCLUDE, GDG (+1), PROC and SYSOUT — a bounded subset. mainframe-frontier shows the shape but is too early to depend on; its Apache license allows borrowing.
- Hercules/MVS 3.8j is useful as a **third lane for IBM semantics** (true EBCDIC, true DFSORT-era collation and sign handling, real JES2 COND/abend behaviour), not as the primary oracle, because (a) its COBOL is OS/VS COBOL (ANSI-74): COBOL-85 `END-IF`, inline PERFORM, intrinsic functions, `ORGANIZATION INDEXED` in the program won't compile; (b) moving datasets in/out needs tape/card images; (c) the legal status is "murky" rather than clean. z/OS with Enterprise COBOL is not an option outside IBM's own programs (Wazi/ZD&T, licensed).
- The customer's own mainframe output is the gold reference anyway; GnuCOBOL's role is to let the oracle run on every commit without mainframe time, with periodic reconciliation of GnuCOBOL-vs-z/OS on the same inputs to validate the stand-in.

### Gaps
- No open-source DFSORT-compatible utility (control cards: SORT/MERGE FIELDS, INCLUDE/OMIT, INREC/OUTREC, SUM, OUTFIL) with any maturity was found; the subset in mainframe-frontier is the only candidate seen. Writing one for the subset a given shop uses is probably unavoidable.
- No measured pass rate of CardDemo under MVS 3.8j; the dev.to article is one anecdote (six records), not a benchmark.

## Key question 4: The NIST COBOL85 suite — what, where, does it run, what passes

### Takeaway
The NIST CCVS85 suite v4.0 (Oct 1992, public domain, `newcob.val`, 28.2 MB, 512 entries) was available in the corpus, extracted with its own `EXEC85` program, and run through GnuCOBOL's harness: 426 programs, 9748 tests, **9610 pass, 0 fail**, 20 deleted (deliberately disabled by the harness config), 118 "inspect" (visual-inspection items, mostly SQ), in 96 s — exactly matching GnuCOBOL's shipped expected summary. It is the natural conformance corpus for a translator, with two caveats: it tests the 1985 standard core (not IBM extensions, CICS, DB2, or JCL), and its "tests" are self-checking PASS/FAIL lines inside printed reports, so it doubles as a byte-comparison corpus only after you decide how to treat the report headers.

### Cited Findings
- The repo README: "The official NIST CCVS85 (COBOL Compiler Validation System) test suite, version 4.0, dated October 1992 ... `newcob.val`, the population file containing 512 test programs ... in the public domain"; entry types `*HEADER,COBOL,name`, `*HEADER,CLBRY,name` (copy members), `*HEADER,COBOL,name,SUBRTN,name2`, `*HEADER,DATA*,name`; "This file is nearly impossible to find online." — [GitHub: Zaneham/nist-cobol85-test-suite](https://github.com/Zaneham/nist-cobol85-test-suite); local copy `/home/claude/cobol-research/corpus/nist-cobol85-test-suite/newcob.val` (28,210,031 bytes, first line `CCVS85 VERSION 4.0 01 OCT 1992`) **[empirical]**
- Other hosts: GnuCOBOL's Makefile downloads `newcob.val.Z` from a Wayback snapshot of `itl.nist.gov/div897/ctg/suites/` or `newcob.val.tar.gz` from `gnucobol.sourceforge.io/files/`; z390 keeps an extracted tree. — `tests/cobol85/Makefile.am` lines 47–49 **[empirical]**; [GitHub: z390development/nistcobol85](https://github.com/z390development/nistcobol85); [SourceForge gnucobol/files/nist](https://sourceforge.net/projects/gnucobol/files/nist/)
- GnuCOBOL's README for the suite: modules NC (nucleus), SM (COPY), IC (CALL), SQ/RL/IX (sequential/relative/indexed I-O), ST (SORT), RW (REPORT WRITER), IF (intrinsic functions), SG (segmentation), DB (debug), OB (obsolete); CM (COMMUNICATION) excluded; "It is expected that WARNING messages appear"; final step is `diff summary.txt summary.log`. — `tests/cobol85/README` **[empirical]**; mirrored at [fossies](https://fossies.org/linux/gnucobol/tests/cobol85/README)
- How it was run here **[empirical]**: EXEC85 extracted from `newcob.val` with the Makefile's sed edits, compiled `cobc -std=cobol85 -debug -x`; per module an `EXEC85.conf` (`*SELECT-MODULE xx` + the shipped `EXEC85.conf.in`, which fills the `X-nnn` implementor placeholders: file names `XXXXX001..`, `SYSIN`/`SYSOUT`, switches, `GNU-Linux`) drives EXEC85 to write `newcob.tmp`, which `expand.pl` splits into `*.CBL`, `*.DAT`, `lib/*.CBL` and `copy/`; `report.pl` compiles each with `-std=cobol85 --debug`, runs it (with `< X.DAT` where a data file exists), and greps PASS/FAIL/DELETE/INSPECT counts from the printed report into `report.txt`.
- Programs extracted per module: NC 95, SM 13 (+4 subprograms), IC 25, SQ 84, RL 26, IX 29, ST 25, SG 13, OB 5, IF 45, RW 6, DB 15. **[empirical]**
- Result (`/home/claude/cobol-research/tools/nist/summary.log`): `Total 426 426 0 0 9610 0 20 118 9748` — Programs 426, Executed 426, Error 0, Crash 0, Pass 9610, Fail 0, Deleted 20, Inspect 118, Total 9748; total duration 96.08 s on 2 vCPUs. `diff` against GnuCOBOL's shipped `summary.txt` is empty (same numbers; only row order differs). **[empirical]**
- Two harness mismatches had to be fixed, neither a compiler failure: `summary.pl` takes module names not paths; and `report.pl` from the 3.x head passes `-Wno-goto-section` for `IC115A`, unknown to cobc 3.1.2, which made IC114A fail with "module 'IC115A' not found" until the flag was removed. **[empirical]**
- The "deleted" and "inspect" categories: EXEC85.conf's `*KILL-DELETIONS`/`*BEGIN-UPDATE` sections patch or disable specific tests (e.g. IF119A..IF141A statistical functions get a fixed argument list; `SQ106A` skips some read tests). SQ has 89 inspect items (e.g. `SQ101M 57 0 0 0 57`): printer-format tests the suite says a human must check. **[empirical]**
- GCC's own COBOL front end (gcobol) discussion: "no current compiler does pass all modules"; Simon Sobisch says GnuCOBOL is "the single one that nearly passes everything"; the COMMUNICATION module is disabled as obsolete in COBOL85. — [gcc-patches thread](https://www.mail-archive.com/gcc-patches@gcc.gnu.org/msg368220.html)
- A third party already uses the NIST programs as a COBOL→Python translation eval. — [GitHub: AnyEvalOrg/eval-nist-cobol85](https://github.com/AnyEvalOrg/eval-nist-cobol85)

### Inferences
- For a translator, the NIST suite is best used as 426 **self-checking** programs: translate each, run the Java, and require the same PASS/FAIL lines and counts — no original-vs-Java byte diff needed because the test asserts its own expectations. The 9610 passing assertions under GnuCOBOL define the reference; any FAIL in the Java lane is a translator bug by construction (the COBOL asserts standard semantics).
- A byte-for-byte diff of the NIST reports against GnuCOBOL's output is also possible and cheap (they are plain sequential print files), but the CCVS header prints the date/time and compiler-identification lines filled by EXEC85.conf; those lines are the only expected variance and should be masked by position, not regex.
- The suite does not cover IBM extensions a shop actually uses (`COMP-5`, `POINTER` arithmetic, `JSON/XML GENERATE`, CICS/DB2 preprocessors, `GOBACK` in nested programs, Enterprise COBOL date intrinsics), so it is necessary, not sufficient.

### Gaps
- Not run: `make test-O` (optimized), the 4.x branch, or the `-std=ibm` dialect against the suite (GnuCOBOL tests it with `-std=cobol85`). Whether all 9610 still pass under `-std=ibm` is unknown and relevant, since the translator's input dialect would be IBM's.

## Key question 5: EBCDIC vs ASCII — what the oracle must normalize vs refuse to normalize

### Takeaway
GnuCOBOL runs in ASCII with `native EBCDIC: no`; sign overpunch, collation and `PIC X` byte values therefore differ from the mainframe at the byte level even when the program logic is identical. The oracle must keep the two lanes in the **same** encoding and compare there; it must never transcode byte-blind, must treat `COMP-3`/`COMP` as opaque, and must refuse to "normalize" collation differences, because those change program results (sorted order, range tests), not just their representation.

### Cited Findings
- `cobc --info`: `native EBCDIC: no`; option `-fsign=[ASCII|EBCDIC] define display sign representation`. **[empirical]**
- Overpunch probe (`runs/carddemo/ovp.cbl`) **[empirical]**: `PIC S9(5) VALUE -12345` is stored as hex `31 32 33 34 75` by default (ASCII `'u'` = 0x75 for −5, GnuCOBOL's ASCII sign nibble scheme) and `31 32 33 34 4E` with `-fsign=EBCDIC` (`'N'` = 0x4E, which is the IBM zoned code D5 ... after ASCII translation of EBCDIC `0xD5` 'N'); positive `+12345` is `31 32 33 34 35` by default and `31 32 33 34 45` (`'E'`) with `-fsign=EBCDIC`. On a real mainframe the same field is `F1 F2 F3 F4 D5` / `F1 F2 F3 F4 C5`. `COMP-3` is `12 34 5D` and `COMP` (binary, 4 bytes) is `FF FF CF C7` in both modes — codepage independent (byte order is big-endian in GnuCOBOL by default, matching IBM).
- Collation probe **[empirical]**: with `PROGRAM COLLATING SEQUENCE IS <alphabet EBCDIC>` the comparison `"a" < "A" < "1"` holds (EBCDIC order: lowercase < uppercase < digits); without it, `"1" < "A" < "a"` (ASCII). The same flag affects `SORT` key order. CardDemo keys are digits only, so unaffected; mixed-case or punctuation keys would sort differently between lanes.
- The course data file is EBCDIC with packed fields embedded; a byte-blind transcode of the 170-byte records would corrupt the two `COMP-3` fields, and a field-aware one (cp037 for `PIC X`, pass-through for `COMP-3`) was required to get correct output. **[empirical]**
- CardDemo ships the same datasets in both encodings; in the ASCII copies the overpunched trailing digit appears as `{` for +0 (`00000001940{`), which is the classic EBCDIC-C0→ASCII mapping of `0xC0` to `'{'` — i.e. AWS's ASCII conversion preserved IBM sign zones as ASCII characters. GnuCOBOL's default ASCII sign scheme would write `0` for +0 in the same field. **[empirical, `data/ASCII/acctdata.txt`]**
- Line-sequential vs record-sequential: GnuCOBOL `LINE SEQUENTIAL` strips trailing spaces unless `COB_LS_FIXED`, and escapes binary bytes only with `COB_LS_NULLS`; `RECFM=F` datasets must be declared `ORGANIZATION SEQUENTIAL` (fixed, no terminators) to compare bytewise. — `/etc/gnucobol/runtime.cfg` **[empirical]**; observed with the 30- vs 80-byte DATEPARM status-04 failure.
- The "Zero Variance" team avoided the problem entirely by comparing at the database layer, and still needed `BigDecimal` `HALF_UP` to match packed arithmetic. — [dev.to](https://dev.to/banuap/zero-variance-proving-cobol-to-java-semantic-equivalence-with-a-live-mainframe-emulator-on-aws-1ani)

### Inferences
- **Normalize (and only with the copybook in hand):** encoding of `PIC X`/`PIC 9 DISPLAY` text between cp037/cp1140 and ASCII/Latin-1 by field; the two sign-zone schemes for `DISPLAY` signed numerics (map 0x7X/0x4X-ASCII schemes ↔ C/D zones) by field; RECFM=V RDW vs `COB_VARSEQ_FORMAT` prefixes; line terminators for SYSOUT/print files; the known-variable report headers (date/time, job name) by column position. Each normalization is itself a translation of a typed value, so it must be derived from the record layout (the same Suite-IR-style decision data the compiler already has), not guessed from bytes.
- **Refuse to normalize:** collation-dependent results (sort order, `>`/`<` on alphanumerics, `INSPECT`/`SEARCH` outcomes) — a difference there is a semantic bug in the Java (or a missing `Collator` for EBCDIC order), not a representation artefact; rounding/truncation of arithmetic (`ROUNDED`, `ON SIZE ERROR`, intermediate precision); numeric overflow and truncation (`PIC 9(3)` receiving 1234); `COMP-3` and `COMP` bytes (compare exactly); record counts and lengths; return/abend codes.
- Best practice is to make the Java lane emit **mainframe-faithful bytes** (EBCDIC text, C/D sign zones, big-endian binaries, RDWs) so the oracle compares against an un-normalized mainframe dataset; in the GnuCOBOL-only development loop, configure GnuCOBOL with `-fsign=EBCDIC` and `PROGRAM COLLATING SEQUENCE` / `-fdefault-colseq=EBCDIC` (3.2+) and compare ASCII bytes with only the text-encoding normalization. Two deterministic lanes with one shared encoding is far safer than one lane plus a clever diff.

### Gaps
- `-fdefault-colseq` (GnuCOBOL 3.2) was not available in 3.1.2 to test; only the in-program `PROGRAM COLLATING SEQUENCE` was verified.
- IBM's `NUMPROC`, `TRUNC(BIN|STD|OPT)` and `ARITH(EXTEND)` compile options change results for invalid sign nibbles, `COMP` truncation and intermediate precision; GnuCOBOL has partial analogues (`-fhostsign`, `binary-truncate` in the dialect conf) but no equivalence was measured here.

## Key question 6: Harness spec and effort estimate

### Takeaway
A concrete harness is three parts: a **job model** (pinned inputs: datasets with layouts, DD bindings, parms, clock, switches, stubs), two **runners** (GnuCOBOL lane; Java lane; optionally mainframe/Hercules lane producing the same dataset set), and a **comparator** that works on logical record streams with a copybook and reports the first difference as (dataset, record number, field, column range, both byte values). Everything exercised above fits this shape; the pieces proven here took about three hours of ad-hoc work and would take 6–10 engineer-weeks to make a reusable tool, with the DFSORT subset and job-control interpreter dominating.

### Cited Findings
- Every component of the proposed harness was exercised in this session on real programs: DD binding via `DD_*`, KSDS load in key order from flat data, clock pinning with fractional seconds and TZ, module path for CALLs, LE stubs, SORT step emulation, abend-code capture, logical unload for indexed files, and SHA-256 comparison across repeated runs. **[empirical, `/home/claude/cobol-research/tools/runs/`]**
- GnuCOBOL compile+run cost for 426 programs was 96 s; a single CardDemo job step compiled in ~1 s and ran in well under a second on 300 records. **[empirical]**
- GnuCOBOL's own NIST harness is ~600 lines of Perl (`report.pl`, `expand.pl`, `summary.pl`) and a Makefile; it already does per-program compile, run with stdin redirect, PASS/FAIL scraping and expected-vs-actual diff — a reference for the runner/reporter layer. **[empirical]**
- `mainframe-frontier` lists the JCL subset a realistic batch shop needs and what it left out (PROCs, IF/THEN/ELSE, concatenation, VSAM, restart). — [GitHub](https://github.com/roberjo/mainframe-frontier)

### Inferences (the spec)

**1. Inputs (a pinned "job fixture", one directory, content-addressed):**
- `job.yaml` (or the original JCL plus an overlay): steps in order; per step `pgm`, `parm`, `cond`, and DDs `{ddname → {dataset, disp, recfm, lrecl, org, keylen/keyoff or copybook ref, encoding}}`; `SYSIN` bytes; `SYSOUT` capture names.
- `datasets/` — initial state of every input/updated dataset as fixed-record files in a declared encoding (store the mainframe EBCDIC bytes as the canonical form; derive ASCII for GnuCOBOL by field using the copybook).
- `copybooks/` — layouts for every dataset that will be compared, with REDEFINES/OCCURS DEPENDING resolved by a record-type discriminator where needed.
- `env.yaml` — `COB_CURRENT_DATE` (full: `YYYY-MM-DD HH:MM:SS.hh ±zz:zz`), `TZ`, `COB_SWITCH_n`, `RANDOM` seed policy, dialect flags (`-std`, `-fsign`, colseq), compiler version/image digest, stub list (`CEE3ABD`, `COBDATFT`, DB2/CICS stubs with their canned answers).
- `expected/` — optional: the mainframe's actual output datasets and return codes from the same fixture (gold); otherwise the GnuCOBOL lane's output becomes the reference after it proves self-identical.

**2. Runner (per lane):**
- Resolve DSN→path per step honouring `DISP` (NEW/OLD/MOD/SHR, normal/abnormal disposition), GDG relative generations, `&&TEMP`, `DUMMY`, and concatenation (concatenate fixed files; refuse mixed LRECL).
- Built-in utilities: `IEFBR14`, `IEBGENER` (copy), `IDCAMS` (`DEFINE/DELETE/REPRO` with key order check, `PRINT` optional), `SORT`/`ICEMAN` (DFSORT subset: `SORT/MERGE FIELDS` with CH/ZD/PD/BI/FS types and EBCDIC collation, `INCLUDE/OMIT COND`, `INREC/OUTREC` BUILD, `SUM FIELDS`, `OUTFIL`, `OPTION EQUALS` honoured; everything else → "unsupported" failure, never a guess).
- GnuCOBOL lane: `cobc -x -std=ibm [-fsign=EBCDIC] -I copybooks`, run with `DD_<ddname>=path`, `COB_LIBRARY_PATH` for modules, stdin = SYSIN, stdout/stderr = SYSOUT/SYSPRINT; capture `RETURN-CODE` and abend code from the stub (not just the 8-bit exit).
- Java lane: identical DD→path contract (the translated program takes its file bindings from the same env names), same clock/seed injection points, same stub answers; writes datasets in the same declared encoding/record format.
- Mainframe lane (optional): submit the fixture to z/OS or TK5, pull back datasets with their DCB; this lane is how the GnuCOBOL stand-in is itself validated.
- Run the original lane **twice** before any comparison; non-identical ⇒ report "nondeterministic original" with the field that moved (the hundredths-of-a-second case above) and stop.

**3. Comparator:**
- For sequential datasets: byte-for-byte after record framing (fixed LRECL; RDW-aware for V); for indexed/relative: compare the key-ordered unload, never the physical file.
- First difference reported as `dataset, record #, byte offset, copybook field path (e.g. TRAN-RECORD.TRAN-PROC-TS), column range, lane A bytes, lane B bytes, decoded values (per PIC/USAGE), and record-count/length mismatches`; continue to collect up to N differences grouped by field so one wrong date format shows as one finding over 257 records, not 257 findings.
- Allowed masks are declared, not inferred: a mask is `(dataset, field or column range, reason)` and the report lists every mask applied; the only built-in masks are the harness's own injected values (clock, job name) when a lane cannot inject them.
- Also compare: per-step return codes and `COND` flow (which steps ran), SYSOUT text after line-terminator normalization, dataset dispositions (what exists after the job), record counts.

**4. Conformance corpora to run through it:** NIST CCVS85 (self-checking, 426 programs; require PASS/FAIL parity); CardDemo batch jobs (POSTTRAN, TRANREPT, INTCALC, CREASTMT) with its shipped datasets; the shop's own jobs with production-shaped fixtures.

**Effort (engineer-weeks, one experienced engineer):** job model + DD resolver + DISP/GDG/temp handling 1.5; IDCAMS/IEBGENER/IEFBR14 0.5; DFSORT subset with EBCDIC-aware keys 2–3 (the biggest single item, and open-ended if INREC/OUTREC/OUTFIL grow); GnuCOBOL runner + stubs + determinism checks 1; copybook-driven comparator and report 1.5; NIST + CardDemo integration and CI 1. Total roughly **7.5–9.5 weeks** for a usable v1 on GnuCOBOL only; add 1–2 weeks to stand up a Hercules/TK5 lane with dataset transfer scripts, and more if OS/VS COBOL incompatibilities force per-program adaptation. Running cost is negligible (whole NIST suite in ~100 s on 2 vCPUs).

### Gaps
- Effort figures are estimates from this session's experience and the component list; no comparable published project with effort data was found except the dev.to anecdote (infrastructure-only timings).
- CICS/DB2 batch (programs with `EXEC SQL`/`EXEC CICS`) is out of scope for GnuCOBOL without a preprocessor and stub database; the CardDemo `app-*-db2` variants were not attempted.
