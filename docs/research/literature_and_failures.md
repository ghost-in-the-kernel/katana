# COBOL-to-Java Migration: Literature, Failures, JOBOL, Equivalence Testing, and Proof Artifacts

Scope note: research run 2026-10-03, ~15 search/fetch rounds. Several primary pages (ResearchGate, Semantic Scholar, ACM DL, Wiley) returned 403/429, so some venue details below come from secondary listings and are marked. Vendor material is flagged as such everywhere.

## Key Question 1: Academic literature 2015–2026 on COBOL-to-Java translation (WCA4Z evaluation paper in detail; LLM benchmarks; rule-based tradition; goto elimination; translation validation)

### Takeaway
The IBM WCA4Z papers are the most serious published work on checking COBOL→Java translations, and they openly concede that (a) formal equivalence is treated as out of reach, (b) dynamic testing "has yielded the lowest return on investment" for them, and (c) paragraph-level LLM translation compounds error (90% per paragraph → ~34% for a 10-paragraph program). Nobody in the literature found has applied compiler translation-validation (Pnueli/Necula-style, Alive2-style) to COBOL migration; the closest is IBM's symbolic-execution-generated differential unit tests (ASE 2024 / 2025), which is testing, not proof. The deterministic rule-based tradition (Sneed, Terekhov & Verhoef) produced working but doubled-size, COBOL-shaped Java and has no published equivalence proof either.

### Cited Findings

**IBM, "Quality Evaluation of COBOL to Java Code Transformation" (Froimovich et al., arXiv 2507.23356, 2025)**
- Checkers used: (1) syntactic (non-empty output, no endless repetition, Tree-sitter Java parse, presence of executable statements — "simple and highly reliable"); (2) semantic: variable-access matching (loose, not strict count), PERFORM→method-call matching, middleware-call matching via Needleman–Wunsch alignment of EXEC SQL / EXEC CICS, and hallucination detection (Java variables/middleware calls with no COBOL counterpart); (3) compilation (three modes supported, only skeleton compilation actively used); (4) LLM-as-Judge on a 7-point scale, validated by SME annotation and "partial order" benchmarks (A>B>C variants). — [arXiv 2507.23356v1](https://arxiv.org/html/2507.23356v1)
- Admitted gaps (direct from the paper): formal equivalence proving is "undecidable" and "the semantic gap between COBOL and Java [is] too significant"; dynamic testing "requires access to Z platforms configured correctly" with middleware and "has yielded the lowest return on investment"; ground-truth comparison "requires significant SME effort" and "more than a single correct translation" exists; LaaJ is "generally more error-prone than SMEs" and lacks IBM-middleware domain knowledge; loose matching "produces false positives due to structural differences"; procedure-call hallucination detection "cannot reliably distinguish between legitimate and hallucinated calls." — [arXiv 2507.23356v1](https://arxiv.org/html/2507.23356v1)
- Error compounding statement: "if a program has 10 paragraphs and each is translated with 90% accuracy, the probability of a fully correct program is only about 34%." — [arXiv 2507.23356v1](https://arxiv.org/html/2507.23356v1)
- Fault classes shown (running example, injected): wrong variable access (CA-CUSTOMER-NUM), wrong exception type (CicsException vs CicsConditionException), wrong CICS abend parameter. LaaJ caught 1 of 3 and produced 1 false positive. The paper gives **no aggregate fault statistics, no dataset sizes, no precision/recall for checkers**; benchmarks named are "genapp21" and "IMS2"; Figure 6 reports LaaJ weighted average 5.04 for ADD vs 2 for CALL. — [arXiv 2507.23356v1](https://arxiv.org/html/2507.23356v1)

**IBM, "Automated Validation of COBOL to Java Transformation" (Kumar et al., ASE 2024 tool demo; arXiv 2506.10999)**
- Approach: COBOL → IR → path enumeration with branch-coverage heuristic → SSA → SMT solving to generate inputs; COBOL run under a debugger on a real IBM Z with external resources mocked at breakpoints; outputs (program variables and resource-call results) captured and turned into JUnit assertions against the Java via a "Resource Mapper" that pairs COBOL SQL/file/CICS/IMS statements with Java equivalents. Equivalence is operationalized purely as output equality on generated inputs. — [arXiv 2506.10999](https://arxiv.org/pdf/2506.10999); [ASE 2024 listing](https://conf.researchr.org/details/ase-2024/ase-2024-tool-demonstrations/21/Automated-Validation-of-COBOL-to-Java-Transformation)
- Results: nine programs of 300–1500 LOC; e.g. LGACDB01 100% branch coverage, 4 tests, 22 assertions, 4/4 pass; CHANN11 0/2 pass — the failing case exposed a real transformation bug (loop condition inversion). — [arXiv 2506.10999](https://arxiv.org/pdf/2506.10999)
- Limitations admitted: generated test sets not minimal; "local variable values cannot be asserted in JUnit tests" because scope changes in translation; COBOL/Java test-count mismatch when all branches sit inside a PERFORM block. Related-work claim: "we have not come across any product, tool or research" doing cross-language, cross-platform validation with resource mocking; cites Zhang & Harman's unit-test filtering for Java→Python / Python→C++ as nearest prior work. — [arXiv 2506.10999](https://arxiv.org/pdf/2506.10999)

**IBM, "Automated Testing of COBOL to Java Transformation" (Hans, Kumar et al., arXiv 2504.10548, 2025; ACM DOI 10.1145/3696630.3728548)**
- Scale: Genapp/IMS set 22 programs / 40 paragraphs, 84% full branch coverage (43/51); IBM compiler benchmark 54,284 programs / 94,524 paragraphs, 92.8% full coverage; StarCoder COBOL set 936 programs / 2,871 paragraphs, 94.3% full coverage. Test generation <1 s for 85,657 paragraphs, max 118 s. Z3 used as solver; byte-level data representation. — [arXiv 2504.10548](https://arxiv.org/pdf/2504.10548)
- Transformation bug classes found: logic inversion (UNTIL vs while), variable scope (parameter hardcoded as local, losing input sensitivity), SQL code handling (Java exceptions replacing SQLCODE-based branching), data-type mapping (fixed-length padding vs Java strings). Claimed manual-validation effort reduction 55 min → 10 min. — [arXiv 2504.10548](https://arxiv.org/pdf/2504.10548)
- Limitations: path explosion on loops; cannot test against real DB/CICS without mocks; dead branches lower coverage; SQL error semantics fundamentally different; local variables invisible to JUnit. — [arXiv 2504.10548](https://arxiv.org/pdf/2504.10548)

**Rule-based / deterministic tradition**
- Terekhov & Verhoef, "The Realities of Language Conversions," IEEE Software 17(6), 2000 (venue from IEEE listing; preprint dated 26 May 2000): six difficulty classes — data-type idiosyncrasies, the "homonym problem" (same syntax, different semantics), domain-focus mismatch, operations tied to internal representation (STRING, INSPECT), operator/return-code/indexing differences, and cumulative compensatory artifacts yielding unmaintainable "alien code." They describe converted output as "Java-compliant COBOL programs." Recommended four phases: restructure in source (remove GOTO, introduce subroutines) → syntax swap → heavy restructuring in target → optional type-safety analysis choosing native vs emulated types. — [VU preprint](https://www.cs.vu.nl/~x/cnv/); [IEEE Xplore](https://ieeexplore.ieee.org/document/895180/)
- Sneed, "Automatisierte Migration alter COBOL Programme in Java," Softwaretechnik-Trends 30(2), 2010: Bull/IDS-COBOL system, 93 main programs + 41 subprograms, 200,711 LOC / 2,908 function points, converted with COB2Java using 15 conversion rules; data structures → singleton objects over character arrays; paragraph → method; GOTO → label variable driven by a finite-state-machine controller; REDEFINES handled by char-array positioning. Generated Java ≈ 2× the COBOL size. Original COBOL embedded as comments; XML metadata per method documenting I/O. The paper reports **no regression-test results, no cost metrics**. — [GI Softwaretechnik-Trends PDF](https://fb-swt.gi.de/fileadmin/FB/SWT/Softwaretechnik-Trends/Verzeichnis/Band_30_Heft_2/17-sneed.pdf)
- Sneed, "Migrating from COBOL to Java," ICSM 2010 (DOI 10.1109/ICSM.2010.5609583); Sneed & Erdös, "Migrating AS400-COBOL to Java: A Report from the Field," CSMR-WCRE 2014; Sneed, "Cost-driven software migration: An experience report," J. Software: Evolution and Process 2020 — all exist (listings fetched) but full text was blocked (403/429); content not verified here. — [ACM listing](https://dl.acm.org/doi/10.1109/ICSM.2010.5609583); [ResearchGate listing](https://www.researchgate.net/publication/261355760_Migrating_AS400-COBOL_to_Java_A_report_from_the_field); [Wiley listing](https://onlinelibrary.wiley.com/doi/abs/10.1002/smr.2236)
- De Marco, Iancu, Asinofsky, "COBOL to Java and Newspapers Still Get Delivered," ICSME 2018 (NYT Company): >2M LOC COBOL since 1979 converted with Modern Systems' automated translator; VSAM KSDS → Oracle (one multi-layout file → 97 tables). — [arXiv 1808.03724](https://ar5iv.labs.arxiv.org/html/1808.03724)
- Veerman, "Revitalizing modifiability of legacy assets," CSMR 2003 (listing); Veerman, "Cobol minefield detection," Software: Practice and Experience 2006; "Restructuring of COBOL/CICS legacy systems," Science of Computer Programming 2002 — the VU Amsterdam COBOL restructuring line; not fetched in full. — [IEEE listing](https://ieeexplore.ieee.org/document/1192407/); [Wiley](https://onlinelibrary.wiley.com/doi/abs/10.1002/spe.745); [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0167642302000618)

**Goto elimination**
- Ceccato, Tonella, Matteotti (FBK-IRST), "Goto Elimination Strategies in the Migration of Legacy Code to Java," CSMR 2008 (legacy BASIC-like language, not COBOL): pattern-based removed 21% of gotos (+13% mean max nesting depth, 1h); Böhm–Jacopini top-level switch removed 79% (+46% depth, 22 s); Erosa–Hendren removed 100% but blew nesting to +232%/+381% and took 117–144 hours, judged "unmaintainable"; JGoto (bytecode-level goto) 0% removal, 0 cost. Chosen hybrid: patterns + Böhm–Jacopini + JGoto for the rest. **No formal correctness check of transformations described.** — [CSMR 2008 PDF](https://profs.scienze.univr.it/~ceccato/papers/2008/csmr2008.pdf)

**Translation validation / differential testing (compiler world)**
- Le, Afshari, Su, "Compiler validation via equivalence modulo inputs," PLDI 2014 (listing only; page blocked). Alive2 "bounded translation validation for LLVM," PLDI 2021; translation validation for V8 JIT, ICSE 2024; "LLVM Translation Validation Automated with LLMs and Lean," arXiv 2609.19583 (2026). None of these target COBOL. — [Semantic Scholar EMI](https://www.semanticscholar.org/paper/Compiler-validation-via-equivalence-modulo-inputs-Le-Afshari/79bbd54d5bdfd20980e5f9a65480f5e127fc1221); [Alive2](https://dl.acm.org/doi/10.1145/3453483.3454030); [V8 TV](https://dl.acm.org/doi/10.1145/3597503.3639189); [arXiv 2609.19583](https://arxiv.org/html/2609.19583)

### Inferences
- The only published equivalence evidence for COBOL→Java is test-based (symbolic-execution inputs + output comparison), at paragraph granularity, with mocked resources; nobody has published a translation-validation-style proof for a COBOL→Java step. A deterministic compiler whose refactoring passes are each checked output-identical would be filling a gap the IBM papers explicitly name.
- IBM's "lowest ROI" verdict on dynamic testing is about *LLM paragraph translation needing a Z box*; a deterministic literal-Java intermediate that runs off-mainframe changes that economics, because the pinned golden can be exercised without z/OS once the runtime semantics (numerics, file I/O) are emulated.
- Sneed's 2× size and FSM-controller-for-GOTO design is exactly the "literal Java" shape the feasibility study proposes as an intermediate; the literature treats that shape as the end product (hence JOBOL), not as a pinned golden to refactor away from.

### Gaps
- Could not retrieve Sneed's ICSM 2010 / CSMR-WCRE 2014 / JSEP 2020 full texts (403/429), so his actual regression-testing method and cost numbers are unverified here.
- The WCA4Z quality paper gives no dataset sizes or fault-rate statistics; no published per-fault-class frequency for LLM COBOL translation was found.
- No paper found that applies EMI or Pnueli/Necula translation validation to COBOL or any business-language migration.

## Key Question 2: Documented migration failures and troubled projects, with causes

### Takeaway
The well-documented disasters (TSB 2018, Co-op Bank/Finacle 2013, Phoenix 2016–) are not language translations but they share one lesson: failures came from untested configurations, cancelled pilots, missing end-to-end testing and governance, not from the code that was tested. The one detailed COBOL→Java post-mortem found (NYT, ICSME 2018) says testing consumed 70–80% of the project, slipped it a year, and still missed a date-overflow defect and a batch-concurrency corruption that surfaced only in production.

### Cited Findings
- **Terekhov & Verhoef (2000)**: three companies went bankrupt and two departments were dismantled after failed conversion projects; one organization spent $50M on failed language conversions; Robert Glass case where converters were "10 times as complicated as was expected." Restructuring examples: one codebase with a GO TO every 4 lines, another every 225 lines. — [VU preprint](https://www.cs.vu.nl/~x/cnv/)
- **NYT Company COBOL→Java (ICSME 2018)**: date-computation overflow (147-day field limit) caused runtime exceptions not caught in testing; multi-layout VSAM → 97 Oracle tables caused performance bottlenecks fixed with an in-memory VSAM cache; unplanned simultaneous batch jobs corrupted output files; millions of DELETE/INSERTs locked the DB for hours. Project delayed one year "primarily due to underestimated testing complexity (70-80% of project time)"; stable after eight months in production; delivered at <10% of the cost of a rewrite; ongoing problem recruiting Java developers who can read the converted code. — [arXiv 1808.03724](https://ar5iv.labs.arxiv.org/html/1808.03724)
- **TSB 2018 (Slaughter and May independent review, 2019)**: two data centres "configured inconsistently" despite specs requiring identical setups; "despite extensive testing, this configuration issue was not identified prior to migration"; nine dress rehearsals and a 1,600-employee pilot did not catch it; all five million customers affected; board relied on executive attestations and supplier assurances. Additional "issues around coding and capacity." — [TSB release](https://www.tsb.co.uk/news-releases/slaughter-and-may.html); [Silicon UK](https://www.silicon.co.uk/cloud/datacenter/data-centre-test-tsb-316443)
- **Co-operative Bank / Infosys Finacle (Kelly Review, 2014)**: £148.4M written down when scrapped in 2013; estimate grew from £184M to £948M, descoped to £663M; causes: CIO departure (2008), "bank in a box" framing that misled the board, ignored KPMG warnings, "significant programme management dysfunctionality." — [Computer Weekly](https://www.computerweekly.com/news/2240219910/Co-operative-bank-report-reveals-challenge-of-legacy-IT-replacement); [Kelly Review PDF](https://assets.ctfassets.net/5ywmq66472jr/3LpckmtCnuWiuuuEM2qAsw/9bc99b1cd941261bca5d674724873deb/kelly-review.pdf)
- **Phoenix pay system (Canada, OAG 2017/2018)**: pilot cancelled June 2015; "lack of true end-to-end testing"; only 6 of 200 custom programs analyzed by Sept 2017; ~232,000 of 290,000 employees affected, 153,000 mis-paid by July 2018; budget $309M → $954M spent by 2018 → >$5.1B by 2025; "an incomprehensible failure of project management and oversight." — [Wikipedia summary of OAG reports](https://en.wikipedia.org/wiki/Phoenix_pay_system); [Global News](https://globalnews.ca/news/4238815/auditor-general-phoenix-pay-system-second-report)
- **US state unemployment systems 2020**: IEEE Spectrum reports the crisis was claim volume (6.6M claims in one week; Connecticut processed 18 months of applications in 3 weeks; Florida reverted to paper), with manual steps in the process as the bottleneck, not COBOL itself; Connecticut's ReEmployUSA modernization was in flight; Maine and Rhode Island had problems with that system (no costs given). — [IEEE Spectrum](https://spectrum.ieee.org/cobol-programmers-answer-call-unemployment-benefits-systems); [NPR](https://www.npr.org/2020/04/22/841682627/cobol-cowboys-aim-to-rescue-sluggish-state-unemployment-systems)
- **GAO**: GAO-19-471 (2019), GAO-23-106821 (2023), GAO-25-107795 (2025) track ten critical federal legacy systems; FedScoop reports most still not modernized years later. These are status audits, not post-mortems of translation projects. — [GAO-25-107795](https://files.gao.gov/reports/GAO-25-107795/index.html); [FedScoop](https://fedscoop.com/the-gao-flagged-10-critical-legacy-it-systems-years-later-most-havent-been-modernized/)
- **Numeric semantics as a live hazard even inside IBM's own compiler**: APAR PH64935 (closed Feb 2025) — Enterprise COBOL 5/6 rounded to 33 instead of 31 decimal places under ARITH(EXTEND) with NUMVAL*, and under ARITH(COMPAT) violated alignment rules on MOVE/COMPUTE of floating-point into shorter decimal receivers, producing results differing from COBOL 4.2 in the last digit. — [IBM APAR PH64935](https://www.ibm.com/support/pages/apar/PH64935)

### Inferences
- Across cases the recurring root causes are: environment/config not under test (TSB), cancelled or truncated pilots (Phoenix), data/numeric edge cases outside the test corpus (NYT date overflow), performance of translated I/O patterns (NYT), concurrency/scheduling not reproduced in test (NYT), and governance (Co-op). A proof-of-equivalence product addresses only the code-semantics slice; the study should say so explicitly.
- PH64935 shows COBOL numeric semantics vary even between IBM compiler releases and ARITH options; a "pinned environment" claim must name compiler version and ARITH/TRUNC/NUMPROC options or it is not reproducible.

### Gaps
- No audited post-mortem of a *COBOL→Java automated translation* that failed outright was found in 2015–2026; Terekhov & Verhoef's bankruptcies are anonymized and from 2000. Sneed's accounts of troubled conversions could not be read (paywalls).
- Commonwealth Bank, Danish/Dutch government cases, and NJ unemployment post-mortems were not researched in depth within the time box.

## Key Question 3: The "JOBOL" problem — origin, what it looks like, documented maintenance costs

### Takeaway
"JOBOL" is attributed to Jason Bloomberg (Intellyx) in 2022 trade press and is consistently defined as Java that preserves COBOL structure and semantics; the concept predates the word (Terekhov & Verhoef's "Java-compliant COBOL programs," 2000). No source found gives measured post-migration defect rates or maintainability metrics; the only hard number is Sneed's ~2× LOC expansion and the NYT recruiting difficulty.

### Cited Findings
- Attribution: TechTarget (Aug 2022) says Jason Bloomberg, Intellyx, introduced "JOBOL" as "Java code with COBOL syntax." Nick Twyman (Truss) calls the output "stilted" Java that "doesn't convey its intent to modern programmers." — [TechTarget](https://www.techtarget.com/searchsoftwarequality/news/252523671/COBOL-programming-skills-gap-thwarts-modernization-to-Java)
- Intellyx (July 2022, **sponsored by CloudFrame**, disclosed): JOBOL = "generated Java code that still retains COBOL syntax"; patterns listed: classes instantiating variables with COBOL group/elementary structure, Java strings standing for COBOL data names, deeply nested IFs, retained COBOL hierarchies instead of POJOs, GO TO emulation; "virtually unmaintainable." No numbers. — [Intellyx](https://intellyx.com/2022/07/16/modernizing-your-mainframe-cobol-beware-the-jobol-pitfall/)
- DZone (Amatam, March 2024): JOBOL = Java "in a procedural style akin to COBOL, without leveraging Java's object-oriented capabilities"; no quantitative claims. — [DZone](https://dzone.com/articles/cobol-to-jobol-a-poor-choice-for-modernization)
- CM First Group / John Rhodes "Overcoming the JOBOL problem" (vendor). — [CM First](https://cmfirstgroup.com/overcoming-the-jobol-problem-when-converting-cobol-to-java/)
- Precursor description, 2000: converted code is "Java-compliant COBOL programs" with "alien code" from cumulative compensations. — [Terekhov & Verhoef](https://www.cs.vu.nl/~x/cnv/)
- Measured shape of rule-based output (Sneed 2010): Java ≈ 2× COBOL LOC; GOTO → FSM controller; data as char arrays in singletons. — [Sneed 2010](https://fb-swt.gi.de/fileadmin/FB/SWT/Softwaretechnik-Trends/Verzeichnis/Band_30_Heft_2/17-sneed.pdf)
- Post-migration people cost (NYT 2018): "ongoing challenges: recruiting Java developers, knowledge transfer across language paradigms." — [arXiv 1808.03724](https://ar5iv.labs.arxiv.org/html/1808.03724)
- Vendor maintainability claim (AWS Blu Age): output "receives an AAAA rating from SonarQube using the customer's SonarQube profile"; no LOC-expansion, complexity, or defect numbers. — [AWS blog (vendor)](https://aws.amazon.com/blogs/migration-and-modernization/aws-blu-age-code-maintainability/)
- Goto-elimination cost evidence (CSMR 2008): complete structured goto removal (Erosa) raised mean max nesting depth +232–381%, i.e., "structured" output can be *less* maintainable than retaining gotos. — [CSMR 2008](https://profs.scienze.univr.it/~ceccato/papers/2008/csmr2008.pdf)

### Inferences
- JOBOL is a marketing word for a 25-year-old observation. The feasibility study can cite Terekhov & Verhoef for the phenomenon and the 2022 trade press for the name.
- The absence of any measured maintainability data is itself a finding: a product that *measures* the refactoring distance from literal Java (and proves each step) would produce numbers nobody currently publishes.

### Gaps
- No peer-reviewed or audited numbers on post-translation defect rates, change-request cost, or maintainability indices for JOBOL-style code were found.
- Bloomberg's own first use of the term was not located; attribution rests on TechTarget's statement.

## Key Question 4: Differential / equivalence testing in practice (parallel runs, record/replay, tools)

### Takeaway
Serious shops rely on parallel running with output comparison: Google's Dual Run (originating at Santander) runs mainframe and cloud side by side on production traffic and diffs outcomes until they match, then flips primary; the NYT ran seven staged environments and black-box group comparisons; IBM generates mainframe-captured differential unit tests. No open-source, record-layout-aware batch output comparator was found; the claims about typical coverage are vendor claims.

### Cited Findings
- **Google Cloud Dual Run** (vendor): stage 1 mainframe primary, cloud secondary; all batch and transaction workloads replicated; "outcomes from both systems are compared to report differences"; functional and performance differences observed; data periodically re-synchronized; continues "until migrated application quality matches mainframe results"; stage 2 swaps primary. "Most of your migration time will be spent in the first stage." Technology built by Banco Santander. No duration or coverage numbers. — [Google Cloud blog](https://cloud.google.com/blog/products/infrastructure-modernization/dual-run-by-google-cloud-helps-mitigate-mainframe-migration-risks)
- **NYT (ICSME 2018)**: "black-box testing of component groups" comparing legacy vs modernized outputs; seven progressive stages from dev machines to production data; parallel mainframe test region; dynamic test-data generation; still missed a date overflow and batch-concurrency corruption. — [arXiv 1808.03724](https://ar5iv.labs.arxiv.org/html/1808.03724)
- **IBM WCA4Z** differential unit tests: COBOL executed under debugger on Z with mocks, outputs become JUnit assertions; branch-coverage-driven input generation. — [arXiv 2506.10999](https://arxiv.org/pdf/2506.10999)
- **IBM quality paper**: dynamic testing "requires access to Z platforms configured correctly" and had "the lowest return on investment" for them. — [arXiv 2507.23356v1](https://arxiv.org/html/2507.23356v1)
- **Independent practitioner artifact** (Josef Stephens, GitHub, 2025/26): behavioral-equivalence check of one synthetic AI-migrated batch program; 7 findings — 4 verified correct, 2 divergences needing fixes, 1 blocking risk (loss of fixed field width in edited-display output; uncertainty about record physical encoding "gates cutover regardless of how clean the arithmetic looks"); author notes bias because translation and validation were in the same session. — [GitHub](https://github.com/stephensjosef-cloud/cobol-behavioral-equivalence)
- **Astadia "Automated Testing in Mainframe Migrations"** and other integrator pages exist (vendor; not fetched in depth). — [Astadia](https://www.astadia.com/blog/automated-testing-in-mainframe-migrations)
- Open-source attempt at a GnuCOBOL parity harness: COG-GTM/COBOL-Legacy-Benchmark-Suite PR #300 "port PORTVALD validation subroutine to Java with GnuCOBOL parity harness" (AI-authored PR). — [GitHub PR](https://github.com/COG-GTM/COBOL-Legacy-Benchmark-Suite/pull/300)

### Inferences
- Industry practice is empirical: production-traffic diffing for months, not proof. The record-layout-aware comparison (edited pictures, COMP-3 bytes, fixed widths, EBCDIC/ASCII) is exactly where the one independent artifact found its blocking finding, so a comparator that understands PIC clauses and physical encodings is a credible differentiator.
- Where coverage is reported at all (IBM), it is branch coverage of the COBOL at paragraph level, 84–94%, driven by symbolic execution — a plausible bar for a proof artifact's "path coverage of the COBOL" claim.

### Gaps
- No public, layout-aware batch file comparator (open or IBM product name) was identified in the time box; IBM File Manager / SuperC-style tools were not researched.
- No published typical parallel-run durations or coverage percentages from a migration shop; Dual Run gives none.

## Key Question 5: What a credible "proof" artifact looks like; borrowable standards (DO-178C tool qualification, CompCert)

### Takeaway
The nearest precedents are CompCert's qualification experience under DO-178C and NASA's Formal Methods Tool Qualification report: they frame a translator's trustworthiness as (a) a specification of source and target semantics, (b) evidence per transformation step, and (c) tool-qualification data showing the checker itself is trustworthy. The IBM papers and the independent artifact together suggest the artifact must include: pinned compiler/ARITH options, per-path inputs with branch coverage numbers, byte-level output diffs with record layouts, and an honest list of untestable constructs.

### Cited Findings
- CompCert, "Practical Experience on Integrating and Qualifying a Formally Verified Optimizing Compiler," ERTS 2018 (Leroy et al.): documents qualifying a verified compiler for use in a DO-178C/IEC 60880 context. — [ERTS 2018 PDF](https://xavierleroy.org/publi/erts2018_compcert.pdf); [AbsInt DO-178C page (vendor)](https://www.absint.com/qualification/do-178c.htm)
- NASA/CR-2017-219371 "Formal Methods Tool Qualification" (Feb 2017): framework for qualifying formal-methods tools under DO-178C/DO-330. — [NASA PDF](https://shemesh.larc.nasa.gov/fm/FMinCert/NASA-CR-2017-219371.pdf)
- Alive2 (PLDI 2021) and V8 translation validation (ICSE 2024): bounded, per-transformation checking of a compiler's output against its input is an established pattern in compiler engineering. — [Alive2](https://dl.acm.org/doi/10.1145/3453483.3454030); [V8](https://dl.acm.org/doi/10.1145/3597503.3639189)
- IBM: formal equivalence judged out of reach for COBOL→Java because of the semantic gap; testing needs a correctly configured Z environment. — [arXiv 2507.23356v1](https://arxiv.org/html/2507.23356v1)
- IBM compiler behavior differs by release and ARITH option (PH64935). — [IBM APAR](https://www.ibm.com/support/pages/apar/PH64935)
- Independent artifact's gating finding was physical encoding/field width, not arithmetic. — [GitHub](https://github.com/stephensjosef-cloud/cobol-behavioral-equivalence)
- Dual Run markets "regulatory compliance documentation" from production comparison reports (vendor claim). — [Google Cloud](https://cloud.google.com/blog/products/infrastructure-modernization/dual-run-by-google-cloud-helps-mitigate-mainframe-migration-risks)

### Inferences
- A defensible framing for CTO/auditor: "translation validation per pass" (Alive2 vocabulary) for the refactoring stages, plus "differential testing with coverage" for the COBOL→literal-Java stage, plus "tool qualification" (DO-330 vocabulary) for the comparator. The study should not claim formal proof of the COBOL→Java front end; IBM's position that this is infeasible will be the reviewer's default.
- The artifact must pin: COBOL compiler and version, ARITH/TRUNC/NUMPROC/NUMCHECK options, code page, record layouts (copybooks) used to interpret every compared byte, input corpus hash, branch/path coverage achieved, and an explicit "not covered" list (e.g., CICS/IMS calls mocked, SQLCODE paths).

### Gaps
- No standard explicitly covering business-application language migration was found; DO-178C/DO-330 and ISO 26262 are borrowings, not fits. ISO 26262 was not researched.
- No example of an auditor-accepted equivalence report for a COBOL→Java migration was found in public sources.

## Key Question 6: Open benchmarks / corpora usable for a test corpus

### Takeaway
Three kinds of corpus exist: compiler-conformance (NIST CCVS85), raw open-source COBOL (X-COBOL, GitHub mining), and small paired COBOL↔Java sets with tests (COBOL-JavaTrans, 143 pairs; COBOLEval, 146 tasks). IBM's 54k-program compiler benchmark is not public. Licenses: NIST suite has no stated license in GnuCOBOL's README (US government work, generally public domain, but verify); X-COBOL CC-BY-4.0; COBOL-JavaTrans Apache-2.0; COBOLEval on GitHub (license not confirmed here).

### Cited Findings
- **NIST CCVS85 / COBOL85 suite**: 12 modules — NC nucleus, SM COPY, IC CALL, SQ sequential, RL relative, IX indexed, ST SORT, RW report writer, CM communication, IF intrinsic functions, SG segmentation, DB debug, OB obsolete; archive `newcob.val.Z` from NIST (http://www.itl.nist.gov/div897/ctg/cobol_form.htm) or auto-downloaded by GnuCOBOL `make test`; README states no license; pass counts not stated. Also mirrored at z390development/nistcobol85 and GnuCOBOL SourceForge /nist. GCC's new COBOL front end also runs it. — [GnuCOBOL README](https://fossies.org/linux/gnucobol/tests/cobol85/README); [z390 mirror](https://github.com/z390development/nistcobol85); [SourceForge](https://sourceforge.net/projects/gnucobol/files/nist/); [GCC patches thread](https://www.mail-archive.com/gcc-patches@gcc.gnu.org/msg368224.html)
- **X-COBOL** (Ali, Chimalakonda et al., IIT Tirupati; arXiv 2306.04892, 2023; Zenodo v2 Dec 2024): 5,195 COBOL files from 168 repositories, 68.4 MB compressed, CSVs of commit/file/PR metadata; CC-BY-4.0. — [Zenodo v2](https://zenodo.org/records/14269462); [arXiv](https://arxiv.org/abs/2306.04892); [project page](https://mir-sam-ali.github.io/X-COBOL/)
- **COBOLEval** (BloopAI, 2024): 146 HumanEval-derived problems, ~6 tests each, GnuCOBOL harness; GPT-4 pass@1 8.90%, mAInframer-34b 10.27%. — [bloop blog](https://bloop.ai/blog/evaluating-llms-on-cobol); [GitHub](https://github.com/BloopAI/cobolEval)
- **COBOLCodeBench**: 46 tasks from BigCodeBench-Hard (cited in COBOL-Coder; location not verified). — [arXiv 2604.03986](https://arxiv.org/html/2604.03986v1)
- **COBOL-JavaTrans** (from COBOL-Coder, 2026): 143 bidirectional pairs / 286 task samples derived from HumanEval-X, 807 COBOL caller tests; Apache-2.0; packaged as pip wheel `eval-cobol-javatrans` by AnyEvalOrg with SHA-256 pinned data. — [AnyEvalOrg GitHub](https://github.com/AnyEvalOrg/eval-cobol-javatrans)
- **COBOL-Coder training data**: 31,492 compilable GitHub COBOL programs and 225,987 synthetic pairs described; public availability not confirmed. — [arXiv 2604.03986](https://arxiv.org/html/2604.03986v1)
- **IBM internal**: "IBM compiler benchmark" 54,284 programs / 94,524 paragraphs; genapp/IMS 22 programs — not released. — [arXiv 2504.10548](https://arxiv.org/pdf/2504.10548)
- **CodeNet** (IBM): used by TCS for COBOL→Java evaluation. — [ICSE 2024 LLM4Code](https://conf.researchr.org/details/icse-2024/llm4code-2024-papers/22/Translation-of-Low-Resource-COBOL-to-Logically-Correct-and-Readable-Java-leveraging-H)
- **Synthetic enterprise-shaped corpora**: COG-GTM/COBOL-Legacy-Benchmark-Suite (portfolio management system with CICS maps, JCL, VSAM/DB2 defs, built with Claude 3.5 Sonnet; license placeholder "[Appropriate License]"); sentientsergio/COBOLGen synthetic generator. — [COG-GTM](https://github.com/COG-GTM/COBOL-Legacy-Benchmark-Suite); [COBOLGen](https://github.com/sentientsergio/COBOLGen)
- IBM's CICS GENAPP sample (the "genapp21" IBM uses) is IBM SupportPac material; license not researched.

### Inferences
- For a *deterministic* compiler, NIST CCVS85 is the natural first golden corpus: it is designed to exercise standard semantics (numeric editing, truncation, file organizations) with expected outputs, which is what a literal-Java intermediate must reproduce byte for byte. The LLM benchmarks (HumanEval-derived) are algorithmic puzzles and underrepresent PIC/COMP-3/REDEFINES/file I/O — low value as equivalence corpora, useful only for breadth.
- X-COBOL gives realistic syntax variety but no expected outputs; it is a parse/compile-coverage corpus, not an equivalence corpus.

### Gaps
- NIST suite license status not confirmed from a primary NIST page (link is legacy).
- COBOLCodeBench location and license not verified; COBOLEval license not verified.
- No public corpus pairing *real* enterprise COBOL with Java and expected batch outputs was found; this corpus does not appear to exist openly.
