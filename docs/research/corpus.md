# Public COBOL corpus for a deterministic COBOL-to-Java migration compiler

Deliverable on disk: `/home/claude/cobol-research/corpus/` (24 shallow clones, 1.1 GB) with
`MANIFEST.md` (per-repo URL, license, counts, features, oracle-ready paths), `scan.sh` (the
grep-based scanner) and `scan.tsv` (its output). GnuCOBOL 3.1.2 is installed locally (`cobc`) and
was used to verify oracles. All "Source" links below are the repositories themselves; counts are
from `scan.tsv` unless stated.

## Which public repositories hold real or realistic COBOL (not toys)?

### Takeaway
Four sources carry realistic weight: AWS CardDemo (Apache-2.0, Enterprise COBOL, CICS+VSAM+batch+JCL,
30k lines), Rocket/Micro Focus BankDemo (20k lines but a demo-only license), the CNAF production
batch programs inside TypeCobol's test tree (five programs, 2.6k to 214k lines each, CeCILL-C), and
the GnuCOBOL contrib tree (250k lines of GnuCOBOL tools, GPL). The NIST CCVS85 suite (~350k lines,
public domain) is the semantic backbone and is mirrored in five of the clones. No government COBOL
application source was found on GitHub.

### Inferences
- CardDemo is the only Apache-licensed, realistic, multi-program business application with JCL and
  data; it should be the primary end-to-end target. BankDemo is comparable in shape but its license
  limits it to private study.
- The CNAF programs are the only production-scale single programs (CGMX02 at 214k lines is 50x
  CardDemo's largest). They are generator output (Install/1), so they stress REDEFINES/COMP-3 data
  layouts and parser limits rather than control-flow idiom.
- ACAS is the largest open (GPL) real application and is worth fetching from another network when
  possible; its absence is the biggest gap in the corpus.

### Gaps
- No public government COBOL application source exists on GitHub as far as the searches found.
- ACAS could not be cloned (SourceForge refused through the proxy); `aimozart/cobol-z`,
  `awsong/MMSECOBOL` and `cobol-programming-course-2` clones failed (missing/private).

## Per-repo dialect, counts and language features

### Takeaway
The corpus spans four dialects: standard COBOL-85 (NIST), IBM Enterprise COBOL (CardDemo, CNAF,
OMP course, zopeneditor, dscobol Mainframe), Micro Focus/Rocket (BankDemo, UT samples) and GnuCOBOL
extensions (contrib, examples). The hard features are present in volume: GO TO (NIST 21,983 hits,
contrib 1,922, BankDemo 392), PERFORM THRU (NIST 2,546, contrib 1,987), ALTER (NIST 193, nowhere
else), ODO (CardDemo 21, BankDemo 18, NIST 17), COMP-3 (CNAF ~65k, contrib 223, dscobol 113), SORT
(contrib 74, NIST 29), EXEC CICS (CardDemo 240, BankDemo 204) and EXEC SQL (contrib 277, dscobol 213,
BankDemo 122).

### Cited Findings
All rows from `/home/claude/cobol-research/corpus/scan.tsv` (grep line counts over each repo's COBOL files):
- CardDemo: CICS 240, SQL 32, REDEFINES 106, ODO 21, COMP-3 32, GO TO 186, ALTER 0 (4 hits are
  `ALTERNATE RECORD KEY`), PERFORM THRU 70; 12 batch programs have 0 CICS and 0 SQL —
  [CardDemo](https://github.com/aws-samples/aws-mainframe-modernization-carddemo)
- BankDemo: CICS 204, SQL 122, SORT 0, RED 50, ODO 18, COMP-3 12, GO TO 392, THRU 136 —

- nistcobol85 (COBOL-85): SORT 29, RED 4,597, ODO 17, COMP-3 0, GO TO 21,983, ALTER 193, THRU 2,546;
  11 programs have COMMUNICATION SECTION, 7 REPORT SECTION, 14 use segmentation —
  [nistcobol85](https://github.com/z390development/nistcobol85)
- TypeCobol (Enterprise COBOL + NIST copy): 1,346 files, 990,727 lines, RED 6,257, ODO 64,
  COMP-3 64,979, GO TO 13,077, ALTER 44, THRU 1,383, SQL 188, CICS 9 —
  [TypeCobol](https://github.com/TypeCobolTeam/TypeCobol)
- gnucobol-contrib (GnuCOBOL): SQL 277, SORT 74, RED 317, ODO 6, COMP-3 223, GO TO 1,922, THRU 1,987 —

- Rocket UT samples: 46 programs, CICS 13, SQL 47, RED 24, GO TO 55, THRU 50; restrictive Rocket

- proleap-cobol-parser: 759 COBOL files (349,204 lines; NIST plus ~300 feature programs with `.tree`
  parse expectations), MIT — [uwol/proleap-cobol-parser](https://github.com/uwol/proleap-cobol-parser)
- cobol-unit-test: largest `src/main/cobol/ZUTZCPC.CBL` 4,426 lines, GPL-3 — [neopragma/cobol-unit-test](https://github.com/neopragma/cobol-unit-test)

### Inferences
- ALTER exists only in the NIST OB/NC modules; a compiler can treat ALTER as "NIST-only legacy" and
  still claim coverage of every realistic sample in this corpus.
- SORT in realistic code is split between the JCL SORT step (CardDemo COMBTRAN) and in-program SORT
  (contrib, NIST ST module); both forms need support for byte-identical batch output.
- COMP-3 arithmetic and REDEFINES over packed fields are where the CNAF programs will break a
  naive Java mapping; they are the right stress test for the "literal Java" intermediate.

### Gaps
- Grep counts are line hits, not statement counts; identifiers containing keywords inflate them
  (e.g. `ALTERNATE`). A parser pass would be needed for exact numbers.
- Dialect per file was judged from repo provenance and compile flags, not by compiling every file.

## Which programs are batch with input and expected output (equivalence oracle)?

### Takeaway
About 760 programs are oracle-ready today: 400 NIST programs with GnuCOBOL-generated reference
REPORT files in `eval-nist-cobol85/reference`, verified byte-identical for NC101A under local
GnuCOBOL 3.1.2; 359 GnuCOBOL autotest programs with byte-exact expected stdout embedded in the
`.at` files; and a handful of textbook update programs with input and output files checked in.
CardDemo's 12 batch programs have inputs but no expected outputs, so their oracle must be generated
by running them under GnuCOBOL.

### Cited Findings
- `eval-nist-cobol85/reference/<MODULE>/` holds per program the expanded `.CBL`, `.cobc.out`, `.out`
  and the REPORT `.log`; 400 `.log` files >1 KB (NC 92, SM 16, IC 25, SQ 83, RL 33, ST 34, SG 11,
  OB 8, IF 43, RW 5, DB 10, IX 40), 388 contain PASS lines; NOTICE says generated 2026-09-20 with
  GnuCOBOL 3.2.0 via EXEC85/expand.pl/report.pl, NIST material public domain, package Apache-2.0 —
  [AnyEvalOrg/eval-nist-cobol85](https://github.com/AnyEvalOrg/eval-nist-cobol85)
- Local verification: `cobc -x -std=cobol85 NC101A.CBL && ./NC101A` wrote a 146-line `REPORT` with
  96 PASS / 4 FAIL lines; `diff` against `reference/NC/NC101A.log` after trailing-space strip: 0 lines
  (this session, GnuCOBOL 3.1.2.0)
- The same package's own eligibility filter ships only 16 programs (NC 13, IF 3) for its LLM eval,
  excluding "compilation-only, no-output, interactive-kill, DB debugging, special-grader, and
  no-PASS/FAIL programs" — [eval-nist-cobol85 README](https://github.com/AnyEvalOrg/eval-nist-cobol85/blob/main/README.md)
- GnuCOBOL `run_*.at`/`data_*.at`: of 839 `AT_CHECK([$COBCRUN_DIRECT ./prog], [0], [...])` run checks,
  359 have non-empty expected stdout (regex count over the clone); example `MOVE to edited item (1)`
  in `run_fundamental.at` expects five exact lines — [OCamlPro/gnucobol tests](https://github.com/OCamlPro/gnucobol/tree/gcos4gnucobol-3.x/tests/testsuite.src)
- `Cobol-mainframe/Employeebatch.cbl` ships `sample input txt` and `expected-output.txt` (first
  record: EMPLOYEE ID 100001, JOHN SMITH, IT, 0075000.00) — [manasachowdary840-collab/Cobol-mainframe](https://github.com/manasachowdary840-collab/Cobol-mainframe)
- dscobol ABCFP chapter 10 (`GnuCOBOL/Tutorials/ABCFP/cbl/BDS1001-BDS1005.cbl`) with
  `data/c10-*master.dat.txt`, `c10-*trans.dat.txt` inputs and `c10-*newmast.dat.txt` outputs checked
  in; `jcl/BDS1003.sh` shows the run (`cobc -x ... -I ../cpy` then execute) — [dscobol/Cobol-Code](https://github.com/dscobol/Cobol-Code)
- CardDemo batch programs (0 CICS/0 SQL): CBACT01C 430 lines, CBACT02C 178, CBACT03C 178, CBACT04C
  652, CBCUS01C 178, CBTRN01C 494, CBTRN02C 731, CBTRN03C 649, CBSTM03A 924, CBSTM03B 230, CBEXPORT

  300 daily transactions, 51 disclosure groups, 50 tcat balances, 18 categories, 7 types) and EBCDIC

- Local compile of CardDemo with `cobc -x -std=ibm -I app/cpy`: CBACT01C, CBTRN02C, CBTRN03C,
  CBSTM03B compiled with 0 errors; CBACT04C failed only because its PROCEDURE DIVISION has USING
  (needs `-m` or a driver) (this session)
- CardDemo batch inputs are VSAM KSDS (`ORGANIZATION IS INDEXED`, `ALTERNATE RECORD KEY`); e.g.
  CBTRN02C selects DALYTRAN, TRANFILE, XREFFILE, DALYREJS, ACCTFILE, TCATBALF — [CBTRN02C.cbl](https://github.com/aws-samples/aws-mainframe-modernization-carddemo/blob/main/app/cbl/CBTRN02C.cbl)
- BankDemo batch: `sources/cobol/core/ZBNKPRT1.cbl` 659 lines, ZBNKEXT1, ZBNKLOAD, ZBNKE15/E35 sort
  exits, JCL `ZBNKBAT1/ZBNKEXT1/ZBNKPRT1.jcl`, data `datafiles/MFI01V.MFIDEMO.*.dat`; no expected
  outputs — [BankDemo](https://github.com/RocketSoftwareCOBOLandMainframe/BankDemo)

### Inferences
- The NIST REPORT files are the strongest oracle: self-checking programs whose output is both a
  byte-exact artifact and a semantic PASS/FAIL ledger, so a mistranslation shows up twice.
- For CardDemo the oracle pipeline is: load ASCII data into GnuCOBOL indexed files with a small
  loader, run each batch program under `cobc -std=ibm`, and freeze its outputs; those frozen files
  then serve the Java side. This is a day of work, not a research problem.
- The GnuCOBOL autotests are the right unit-level corpus for the "proven refactoring passes":
  each isolates one semantic rule (edited MOVE, truncation, ROUNDED, ODO) with exact output.

### Gaps
- No realistic (multi-thousand-line business) program in the corpus ships expected output; all
  realistic oracles must be generated, which ties equivalence to GnuCOBOL's semantics rather than
  IBM's (relevant for COMP-3 edge cases and EBCDIC collation).
- Some NIST modules (SQ, RL, IX) create files whose binary layout is GnuCOBOL-specific; only the
  REPORT text, not the data files, should be compared.
- A few NIST programs print DATE/TIME from ACCEPT; these lines need masking (not checked per program).
